## Key Design Decisions
- Board quick-assess (phase 5, pre-plan; red flags only reflect that no phase-5 artifacts existed yet) adopted as constraints: notification secrets masked and write-only; notification sends with timeouts (10 s), one retry on 5xx/network error, http(s)-only URLs; failures logged (secrets redacted) and surfaced as a health warning; log viewer paginated (no unbounded rendering) and log-file download restricted to files listed in the logs directory (no path input); backup download/delete/restore by file name validated against the backups directory listing; run-now reuses the scheduler/command de-dupe; shared StatusBadge (icon + text + colour); realtime invalidation debounced (250 ms per query key) with polite aria-live for command completions; e2e smoke at desktop (1280x800) and mobile (390x844) viewports with axe checks.
- Migration 0005_notifications.sql: notifications(id, name UNIQUE, implementation webhook|discord|email, on_grab, on_download, on_upgrade, on_rename, on_series_add, on_series_delete, on_episode_file_delete, on_episode_file_delete_for_upgrade, on_health_issue, on_health_restored, include_health_warnings, tags JSON, settings JSON). Webhook settings {url, method POST|PUT, username, password}; Discord {webHookUrl, username, avatar}; Email {server, port, useEncryption 'always'|'preferred'|'never', username, password, from, to[], cc[], bcc[]}. Secrets: password, webHookUrl, url query string are masked as '********' in responses (url shown without credentials/query).
- Notification events mapped from internal events: history grabbed -> Grab; downloadFolderImported -> Download (isUpgrade when an episodeFileDeleted with reason upgrade happened for the same download) ; episodeFileRenamed -> Rename; episodeFileDeleted (reason not upgrade) -> EpisodeFileDelete; series created -> SeriesAdd; series deleted -> SeriesDelete; health issue added/cleared -> Health/HealthRestored. Payloads follow Sonarr's webhook schema shape {eventType, instanceName, applicationUrl, series {id,title,path,tvdbId,tvMazeId,type}, episodes [{id, episodeNumber, seasonNumber, title, airDate}], release {quality, releaseTitle, indexer, size}, episodeFile {relativePath, path, quality}, isUpgrade, downloadClient, downloadId, health {level, message, type}}. Email: a dependency-free SMTP client over node:net/node:tls (EHLO, STARTTLS when offered/required, AUTH LOGIN/PLAIN, MAIL/RCPT/DATA with dot-stuffing, QUIT), plain-text + simple HTML body, 15 s timeouts. Sends run asynchronously and never block the triggering operation.
- Logging: a log service writes structured entries to {dataDir}/logs/sonarr.txt (rotate at 1 MB, keep 5: sonarr.0.txt ... ) and keeps the last 2000 entries in memory; Fastify's pino logger streams into it (level from host config logLevel); apikey and passwords redacted. API: GET /api/v3/log (paged, level filter), GET /api/v3/log/file (list), GET /api/v3/log/file/:filename (only names from the list).
- Health checks (recomputed every 5 min via a 'CheckHealth' scheduled command and after relevant config/indexer/client changes): no indexers enabled for RSS/search; all indexers unavailable (backoff); no download client; download client unavailable (queue health); root folder missing/inaccessible; root folder low free space (< 1 GB); recycle bin missing; notifications failing; no API key-protected auth (authentication external without proxy warning). GET /api/v3/health -> [{source, type 'ok'|'notice'|'warning'|'error', message, wikiUrl}]; publishes 'health' events; triggers Health/HealthRestored notifications.
- Backups: zip files written with a dependency-free zip writer (node:zlib deflateRaw + zlib.crc32) containing sonarr.db (via SQLite VACUUM INTO a temp file) and config.json (host config without secrets is not needed: the db holds config); stored in {dataDir}/Backups/{manual|scheduled}/sonarr_backup_v{version}_{yyyy.MM.dd_HH.mm.ss}.zip; scheduled Backup task every 7 days; retention 28 days (housekeeping). Restore: upload or choose an existing backup -> validated zip with sonarr.db -> staged to {dataDir}/restore/sonarr.db -> applied at next start (openDb swaps it in before migrations) -> API returns {restartRequired: true}; POST /api/v3/system/restart spawns a detached copy of the current process (same execPath/argv/env) then shuts down gracefully; POST /api/v3/system/shutdown shuts down.
- Housekeeping command (daily) becomes real: delete commands older than 7 days, prune recycle bin entries older than recycleBinCleanupDays, prune scheduled backups older than 28 days, prune history? no (kept), vacuum the database weekly.
- Updates page: GET /api/v3/update returns [] with a message that self-updating is out of scope (PROJECT out-of-scope list).
- Static UI: in production the server serves web/dist via @fastify/static under urlBase with SPA fallback (non-/api, non-/feed GET requests that accept text/html get index.html with an injected <base href> for urlBase); when web/dist is missing the server logs a hint and skips static serving. Root `npm start` builds nothing; `npm run build` then `npm start` gives a full app on port 8989.
- E2E: @playwright/test added as a root devDependency (only new dependency in this phase), using the preinstalled Chromium (PLAYWRIGHT_BROWSERS_PATH / executablePath /opt/pw-browsers if needed); an e2e server entry server/src/e2e/start.ts boots buildApp with FakeMetadataProvider, a fake indexer factory and a fake download client factory on a temp data dir and port 8990 with the built UI; root script `npm run e2e` builds the web app then runs Playwright. Domain workflow, spec and architecture proposals skipped (autonomous defaults).
