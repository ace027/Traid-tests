## Deferred (Medium Confidence)
- `server/src/services/backup.ts` [major, 65%]: `stageRestore` accepts any valid SQLite file named `sonarr.db` inside a zip. It checks the magic header and `integrity_check`, but not that the file is a Sonarr database. It also doesn't check that the schema isn't newer than this build, for example that the `config` and `series` tables exist and the applied migrations are a subset of the known ones.
- `server/src/services/backup.ts` [minor, 60%]: `writeZip` writes straight to the final path in the listed backup folder. If it fails partway (ENOSPC or an I/O error), a truncated `.zip` stays behind and appears in `listBackups`. The DB is also read fully into memory (`readFileSync`, `deflateRawSync`). Zip32 header fields throw a RangeError for entries over 4 GB.
- `server/src/services/logs.ts` [minor, 50%]: If `rotate()` throws partway (for example a rename failing with EBUSY or EPERM), the empty catch skips the append. `this.size` is not reset, so every later write retries the rotation and throws again.
- `server/src/plugins/staticUi.ts` [minor, 60%]: The "hashed asset" check tests `filePath.split(path.sep).includes('assets')` on the absolute path. If the install path contains an `assets` directory (for example `/srv/assets/sonarr/web/dist`), every non-index file, such as `favicon` or `manifest`, is served as `immutable` for a year.
- `server/src/routes/backup.ts` [critical, 70%]: `defaultLifecycle.restart()` closes the app, then respawns with `spawn(process.execPath, process.argv.slice(1), …)` and calls `process.exit(0)`. It drops `process.execArgv`. The server is started with `tsx src/index.ts` (`npm start`) or `tsx watch` (`npm run dev`), and tsx supplies its loader through `execArgv`. The detached child therefore starts as plain `node …/index.ts`, where the `./app.js` imports of `.ts` sources can't resolve, so it likely crashes. The parent has already exited. If a supervisor such as Docker or systemd restarts the process, the detached child may also fight it for the port.
- `server/src/notifications/dispatcher.ts` [minor, 55%]: The dispatcher is lazily activated through module-level `WeakMap` state (`activators`) and an exported `activateNotificationDispatcher(app)`. Every caller that creates a notification must remember to call it. `providerFactory` and `providerDeps` are also module-level mutable globals used as test hooks (`setNotificationProviderFactory`, `setNotificationProviderDeps`).
- `server/src/notifications/dispatcher.ts` [advisory, 50%]: The implementation switch is repeated in `parseStoredSettings` and `createProvider`. `createProvider` reparses the settings and then casts them (`settings as WebhookSettings`). `secretsOf` is keyed on hard-coded field names ('password', 'webHookUrl', 'url') instead of the per-provider schema.
- `web/src/pages/system/Tasks.tsx` [minor, 60%]: The icon-only RunNowButton has a fixed aria-label ("Run X now"). While the task runs, only the `title` changes to "X is running". The accessible name stays the same, so a screen reader user gets no running state from the button. The `title` text is also not exposed reliably to keyboard or touch users.
- `web/src/pages/system/Events.tsx` [advisory, 60%]: The expand button sets `aria-controls={detailsId}`, but the target `<tr id={detailsId}>` is only rendered while open. When closed, the reference points at a missing element.
- `web/src/pages/system/Backup.tsx` [advisory, 50%]: The RestartBanner has `role="status"` and contains an interactive Restart button. Its text switches between two messages. The banner is mounted already populated, and some screen readers do not announce a live region that is inserted with its content.
- `web/src/pages/system/Backup.tsx` [minor, 60%]: The restart `onSuccess` handler assigns `stopPolling.current` only after the async `loadInitialize()` promise resolves. The unmount cleanup, `useEffect(() => () => stopPolling.current?.(), [])`, runs at unmount and finds `stopPolling.current` still null if the user leaves the page before that. `waitForRestart` is then started afterwards and never stopped.
- `web/src/pages/system/Backup.tsx` [minor, 60%]: The row actions are three adjacent icon-only `size="sm"` ghost buttons. They have no visible labels or tooltips (no `title`). Restore and Delete sit directly beside each other with the same ghost styling. The empty-state text hardcodes "Backups are created every week", which may not match the configured schedule.
- `server/src/services/health.ts` [minor, 75%]: `reportNotificationFailure` and `clearNotificationFailure` only change an in-memory set. They do not schedule a recheck, and `notification` is not in `RECHECK_EVENTS`. The `NotificationStatusCheck` warning therefore appears or clears only on the next scheduled `CheckHealth`, which runs every 5 minutes. The `onClose` hook in `dispatcher.ts` is unaffected.
- `web/src/lib/events.ts` [advisory, 60%]: `eventQueryKeys` carries speculative aliases (`config/host`, `host`, `config/ui`, `ui`). The server only publishes `hostconfig`, `uiconfig` and `config`. The `config` event name is not mapped at all.
- `web/src/pages/system/Tasks.tsx and /home/user/Traid-tests/web/src/components/layout/CommandActivity.tsx` [minor, 70%]: Command-completion detection and the aria-live announcement are implemented twice, in `useCompletionAnnouncement` and in the CommandActivity effect. `humanize` in CommandActivity duplicates `humanizeName` from hooks.ts and lacks its "Rss" to "RSS" handling.
- `e2e/helpers.ts, /home/user/Traid-tests/e2e/smoke.spec.ts, /home/user/Traid-tests/package.json` [minor, 75%]: (a) `e2e/*.ts` and `playwright.config.ts` are outside every workspace tsconfig, so `npm run typecheck` never checks them. (b) The root `e2e` setup imports `axe-core` (declared only in `web/package.json`) and runs `npx tsx` (declared only in `server/package.json`) through hoisting. (c) `page.waitForTimeout(500)` at helpers.ts line 97 is a fixed sleep.
- `server/src/notifications/webhook.ts` [advisory, 50%]: `sendJson` retries once after a network error, a timeout (the abort case), or any 5xx. The POST is not idempotent.
- `web/src/pages/system/Events.tsx` [advisory, 60%]: `data.records.slice(0, EVENTS_PAGE_SIZE)` is redundant, because the server already pages by `pageSize`.
- `web/src/components/layout/CommandActivity.tsx and web/src/pages/system/Tasks.tsx` [minor, 75%]: Two independent `aria-live="polite"` announcers fire for the same command transition. One is in the header, `command-announcer`. The other is on the Tasks page, `task-announcer`. For failures, a toast also fires with the same text.
- `web/src/pages/system/Tasks.tsx` [minor, 55%]: The queue table has 8 columns, and the table sits in an `overflow-x-auto` wrapper. Nothing sets a min-width or collapses columns on narrow viewports. The Started and Ended columns repeat date cells, and the Message column is clamped to `max-w-xs`.
- `server/src/notifications/smtp.ts` [minor, 60%]: With `starttls: 'preferred'`, the default in the schema and UI, a server that does not advertise STARTTLS is used in plaintext. The code then sends `AUTH PLAIN` or `AUTH LOGIN` with the stored password over the unencrypted socket. An attacker who strips the STARTTLS capability from the EHLO reply gets the credentials.
- `server/src/notifications/dispatcher.ts (with server/src/services/health.ts and server/src/index.ts)` [major, 65%]: `HealthService.list` starts empty. The dispatcher subscribes to `onChange` during `buildApp` if any notification exists. The first health check in `index.ts` (and the first `GET /health`) treats every existing issue as `added`. Every restart therefore sends a "Health" notification for each issue that was already known and already notified.
- `server/src/services/backup.ts` [minor, 50%]: `backupPath` and `deleteBackup` resolve a backup by `name` only. The same filename can exist in `manual/` and `scheduled/`, because the name is second-resolution and type-independent (for example a manual and a scheduled backup in the same second). The UI keys rows by `type/name`, but the API and the UI call restore, download and delete by name alone.

- `web/src/components/layout/CommandActivity.tsx` [minor, 60%]: The announcer holds a single string. When several commands finish in one poll, only the last one is announced. When two commands with the same name and status finish one after another (for example, Housekeeping completed twice), `setAnnouncement` receives identical text. React does not touch the DOM, so the live region stays silent the second time.
