## Suggestions (Not Required)
- F-001 `server/src/downloadClients/qbittorrent.ts`: `torrentFile as unknown as ArrayBuffer` is an unsafe cast. The `loggedIn` field is declared after the methods that use it, and it duplicates the state held by `cookie`. (fix: Build the Blob from `new Uint8Array(torrentFile)` (or `torrentFile.slice().buffer`). Move `loggedIn` to the top of the class.)
- F-002 `server/src/services/events.ts`: `publish` takes `Record<string, unknown>`. About 20 call sites (queue.ts:329, blocklist.ts:60, routes/blocklist.ts:49 and 58, routes/downloadclient.ts:139, 157 and 165, and others) work around it with `as unknown as Record<string, unknown>`. (fix: Change the parameter type to `object` or a generic and cast once inside `publish`.)
- F-003 `server/src/downloadClients/nzbget.ts`: `(g.RemainingSizeMB ?? 0) + 0` is a no-op left over from development. (fix: Remove the `+ 0`.)
- F-005 `web/src/pages/series/InteractiveSearchModal.tsx`: The label `release.temporarilyRejected && !release.rejected ? 'Temporarily rejected' : 'Rejected'` can never show "Temporarily rejected". The server sets `rejected = !approved` in `toReleaseResource` (server/src/routes/release.ts:73), and a temporary rejection is also not approved. So `rejected` is always true whenever `temporarilyRejected` is true. (fix: Use `release.temporarilyRejected ? 'Temporarily rejected' : 'Rejected'`.)

## Deferred (Medium Confidence)
- `server/src/services/search.ts` [major, 75%]: `processDecisions` throws the first grab error when nothing in the batch was grabbed. `runEpisodes` does not catch it, so one batch whose grabs all fail (for example a dead .torrent URL, or a client that rejects the release) aborts the whole MissingEpisodeSearch or CutoffUnmetEpisodeSearch. Later batches never run, and neither does the `runSeason` fallback after a failed pack.
- `server/src/services/search.ts` [major, 70%]: `searchIndexers` runs every criterion sequentially inside a single per-indexer call. A batch of 50 episodes on a non-daily, non-anime series issues up to 50 requests per indexer, one per episode. If any one request throws, the whole indexer's results for the batch are discarded and `recordFailure` backs the indexer off.
- `server/src/services/grab.ts` [major, 65%]: After `addRelease` succeeds and history is recorded, `await getQueue(app).refresh()` can still reject (for example on a DB error inside `build()`). `grabRelease` then throws, and release.ts reports 409 "Unable to grab" for a release that is already in the client. `processDecisions` also treats it as a failure and may grab an alternate release for the same episodes.
- `server/src/routes/release.ts` [minor, 70%]: Every error from `grabRelease` is returned verbatim as a 409 message, including non-GrabError exceptions such as SQLite or JSON parse errors.
- `server/src/services/queue.ts` [minor, 70%]: Three problems in the queue service. - The `ids`, `firstSeen` and `ignored` maps are never pruned when items leave the client, so they grow for the life of the process. - `matchFor` runs up to 3 history queries per item on every refresh. Refresh runs every minute and on every grab. - In `remove`, the blocklist entry is written before `removeItem` is awaited. If the client call throws, the item is blocklisted but still in the queue, and the error then returns 400.
- `server/src/services/scheduler.ts` [minor, 55%]: When a task's command is already active because the user started it manually, `enqueueTask` returns false and does not track the active command. When that manual run finishes, `lastExecution` and `nextExecution` never advance. The task stays due and re-runs on the next tick, up to 30 s later. If the process restarts while a scheduled command is running, the command is not tracked either.
- `server/src/services/search.ts, server/src/services/rss.ts` [advisory, 60%]: No test or code path covers the partial-failure cases above: one criterion failing, a grab failing mid-batch, or a post-grab refresh failure. I did not run the verification suites. This review is from reading the code.
- `web/src/pages/series/InteractiveSearchModal.tsx` [minor, 70%]: After a successful grab the button shows "Grabbed" (check icon, ghost variant) but stays enabled. Clicking it again sends a second grab for the same release. The success state is only a color/icon change, and the accessible name switches to "Grabbed <title>" while the control is still an actionable button.
- `web/src/pages/series/InteractiveSearchModal.tsx` [minor, 70%]: Below `md` the table headers are hidden (`sr-only`), so the "Sort by" select is the only sorting control. It has no way to toggle sort direction. Direction is hard-coded to descending for quality, size and peers, and ascending for the others. For example, the smallest size or the oldest age cannot be chosen. The `<label>` wraps the Select, but it is unclear whether Select forwards an accessible name.
- `web/src/pages/activity/Queue.tsx` [minor, 55%]: The status-message popover closes only through its toggle button or Escape while focus is inside the wrapper. There is no outside-click or blur handling. Several popovers can stay open at once. The panel is `absolute` with `z-20` inside a scrolling `overflow-x-auto` table wrapper, and it can be clipped by the wrapper or by the bottom row.
- `server/src/routes/indexer.ts (and server/src/routes/downloadclient.ts)` [minor, 60%]: The two provider CRUD route files are structurally near-identical: list, get, create, update, delete, test, schema, secret masking and validation. They are 188 and 199 lines, and about 344 diff lines remain after normalising the names. The web side repeats this in IndexerModal (454 lines) and DownloadClientModal (242 lines), and in Indexers.tsx and DownloadClients.tsx.
- `server/src/services/search.ts` [minor, 65%]: `processDecisions` returns `rejected`, but no caller uses it. `runEpisodes` reports `found: decisions.length`, which counts rejected decisions as "found". The message "Found N releases" therefore means "evaluated" in some paths. In `runSeason` the pack decisions and the per-episode decisions are both added to `found`, so one release can be counted twice.
- `server/src/services/grab.ts` [minor, 55%]: `JSON.parse(series.tags) as number[]` is an unchecked cast of a JSON column. `grabRelease` also does too much in one function: it picks the client, fetches the torrent, adds the release, records history, refreshes the queue and publishes the event. It also depends on the queue service (`getQueue`), which couples grab to queue.
- `web/src/pages/activity/Queue.tsx` [minor, 75%]: `records = queue.data?.records ?? []` creates a new array on every render while `queue.data` is undefined (initial load, or an error with no data). The `useEffect` that depends on `[records]` then runs after every render during that period. The effect returns `prev`, so there is no render loop.
- `web/src/pages/activity/Queue.tsx` [minor, 65%]: The error banner only renders when `queue.isError && !queue.data`. `keepPreviousData` and the 5s polling keep stale data after a failed refetch, so a persistent failure shows no error. The queue then looks current when it is not. Nothing signals the stale state.
- `web/src/pages/activity/Queue.tsx` [minor, 60%]: The row and header checkboxes are `size-4` (16px) with no enlarged hit area. The remove button is `size="sm"` ghost and icon-only. The 11-column queue table has no stacked/card layout below `md`, unlike the interactive search table, so it relies on horizontal scroll. On touch devices the targets are well under the 44px guideline.
- `web/src/pages/series/InteractiveSearchModal.tsx` [advisory, 50%]: When `target` becomes null on close, `subject` is '' and `params` is null while the Modal may still play its exit animation. The title becomes "Interactive Search - Title " and the body unmounts immediately.
- `server/src/indexers/newznab.ts` [major, 65%]: The info hash is taken from a magnet link with `/xt=urn:btih:([A-Za-z0-9]+)/` and only lowercased. A 32-character base32 btih (valid in magnets) stays base32, so `release.infoHash` is not the 40-character hex hash. The download-client code already has `infoHashFromMagnet` in bencode.ts, which handles base16 and base32.
- `server/src/services/queue.ts` [minor, 55%]: Three problems. 1. `doRefresh` calls `build()` outside any try/catch, and `matchFor` runs unguarded `JSON.parse` on history `quality` and `data`. One corrupt row makes every queue endpoint and the `makeDecisions` call (via `loadQueue`) throw. 2. In `remove()`, the blocklist entry is added before `removeItem` is awaited. If the client call throws mid-loop, earlier items in the bulk call are already removed and blocklisted but the request returns an error. 3. The `ignored` set used for "remove without removing from the client" is memory-only, so those items reappear after a restart.
- `server/src/decision/engine.ts` [minor, 60%]: `isBlocklisted` runs `select ... where series_id` for every release and loads all blocklist rows each time. The other data in `DecisionData` is cached per call; the blocklist is not.
- `server/src/services/queue.ts` [advisory, 60%]: The service imports `pagingSchema` from `../routes/history.js`, and `routes/blocklist.ts` does the same. A service depends on a route module.
- `server/src/indexers/registry.ts and /home/user/Traid-tests/server/src/downloadClients/registry.ts` [advisory, 50%]: The indexer backoff map and the download-client rotation map are module-level singletons, not per-app state. Backoff is lost on restart. The `pickClient` rotation key is per process and not per app.
- `server/src/services/grab.ts and /home/user/Traid-tests/server/src/services/search.test.ts` [minor, 55%]: Tag-based client routing through `grabRelease` has no test. `pickClient` is tested in isolation, but no test sends a tagged series' release through `grabRelease` to the tagged client. There is also no test of torrent redirect or timeout handling beyond the oversized-file case, and no Torznab base32 test (see Finding 1).
- `server/src/services/queue.ts` [minor, 65%]: `remove` calls `addToBlocklist` before `clientFor(row).removeItem`. If the client removal throws (client down, auth failure), the route returns 400. The blocklist row has already been inserted and its event published. The item stays in the queue, and a retry with `blocklist=true` inserts a duplicate blocklist row. Items already processed earlier in a bulk call are also removed without any report to the caller.
- `server/src/downloadClients/registry.ts` [minor, 55%]: `pickClient` treats a client whose `tags` array is non-empty as tagged-only. Deleting a tag (the tag route does not touch indexers or download clients) leaves a stale tag id in the client's `tags`. That client is then never chosen for untagged series. Grabs fail with "No download client is available for usenet/torrent" and the Settings UI shows no tag.
- `server/src/indexers/registry.ts (used from /home/user/Traid-tests/server/src/routes/indexer.ts 112-122, 158-174)` [minor, 60%]: Indexer failure backoff is in memory only. It escalates to 24 hours and is not cleared when the indexer is edited (PUT) or when a single `/indexer/test` of that indexer succeeds. Only `testall` calls `recordSuccess`. A user who fixes a wrong API key still has the indexer skipped by search and RSS for up to the backoff period. The state also resets on restart, which is inconsistent.
- `server/src/services/grab.ts` [minor, 50%]: The `.torrent` download uses `fetch` with `redirect: 'follow'`. Jackett and Prowlarr-style torznab links often answer with a 302 to a `magnet:` URI. `fetch` rejects that redirect, and the failure is reported only as "Unable to download the torrent file". The code never inspects the redirect target. Magnets are only handled when the release already carries `magnetUrl`.
- `server/src/services/queue.ts, server/src/routes/downloadclient.ts, server/src/db/schema.ts` [minor, 60%]: `removeCompletedDownloads` and `removeFailedDownloads` are stored and exposed but nothing in the server acts on them. A failed client item only becomes `failedPending` with an error message. It is never blocklisted, removed, or re-searched. It also stays in the queue, and the `queue` specification keeps rejecting that episode as "Release in queue ...", because failed items are still returned by `details()`.
- `server/src/decision/engine.ts` [minor, 50%]: Any exception thrown while evaluating a release is logged and then reported to the user as "Unable to parse release". Database errors, JSON parse failures in a profile row, and similar problems all get that same message.
- `server/src/decision/engine.ts` [minor, 50%]: A full-season pack that the parser flags as multi-season (for example `S01-S03.COMPLETE`) is mapped only to episodes of `parsed.seasonNumber` (the first season). Other seasons are ignored and the release is not rejected.
- `server/src/routes/indexer.ts, server/src/routes/downloadclient.ts` [minor, 50%]: On create, the mask `********` is accepted as a real value and saved. Indexer POST passes `storedKey` as `undefined`, so `toColumns` stores `''`. Download client POST stores `input.settings` without calling `unmask`, so it stores the literal mask string.
- `server/src/services/blocklist.ts` [advisory, 50%]: `isBlocklisted` runs `select().from(blocklist).where(seriesId)` and then filters in memory. The engine calls it once per release.
- `server/src/routes/downloadclient.ts` [advisory, 60%]: The handler takes `reply` only to call `reply.code(200).send(results)`, which is Fastify's default. The inline result type `{ propertyName; errorMessage }[]` is declared by hand. The indexer `testall` route has the same shape, and `ProviderTestResult` is declared separately in the web code. So the shape is defined in three places.
